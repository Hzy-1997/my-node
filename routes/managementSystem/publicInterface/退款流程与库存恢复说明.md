## 一、四个 `restore*Stock` 函数为什么不一样？

四个库存恢复函数分别对应四种业务模型，它们各自面对的「库存数据结构、存储介质、业务规则、数量恢复方式」完全不同，因此不能合并成同一个函数。

| 函数                  | 行号                                                                                                                                                                | 业务 | 恢复数量来源             | 涉及存储                             |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | ------------------------ | ------------------------------------ |
| `restoreTicketStock`  | [L195](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/routes/managementSystem/publicInterface/publicInterface.js#L195>) | 票务 | `order.buyNum`           | Redis + DB(Ticket) + 购买记录 + 选座 |
| `restorePackageStock` | [L229](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/routes/managementSystem/publicInterface/publicInterface.js#L229>) | 套餐 | `order.buyNum`           | Redis(按日期双 key) + 取消上下文     |
| `restoreHotelStock`   | [L253](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/routes/managementSystem/publicInterface/publicInterface.js#L253>) | 酒店 | `order.roomCount` × 每晚 | Redis + DB(RoomInventory 按日期)     |
| `restoreParkingStock` | [L283](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/routes/managementSystem/publicInterface/publicInterface.js#L283>) | 停车 | 固定 `+1`                | DB(Parking) + Redis 过期 key         |

### 1.1 差异具体说明

#### ① `restoreTicketStock`（票务）

- Redis 库存 key：`ticket:stock:${goodsId}`，用 `incrFun` 累加 `buyNum`
- DB 库存：查 `Ticket` 表后 `update remainingStock + buyNum`
- 额外两步：
  - 删除 Redis 购买记录 `purchase:${memberId}:${goodsId}`（防止重复购买限制被误判）
  - 若 `order.seat` 存在，调用 `ticketPurchaseService.releaseAllSeats` 释放选座
- **为什么不同**：票务是「单品 + 剩余数量」模型，且有「选座」和「购买记录」两个票务独有的概念。

#### ② `restorePackageStock`（套餐）

- 从 Redis 读取 `cancel:data:${orderNumber}` 取消上下文（含 `packageItemId`、`roomTypeId`、`dateRange`）
- 遍历 `dateRange` 每个日期，同时恢复两个 key：
  - `combo:stock:${packageItemId}:${date}`（套餐自身库存）
  - `hotel:roomtype:stock:${roomTypeId}:${date}`（套餐内含酒店的库存）
- 调用 `comboPurchaseService.refundStock(stockKeys, buyNum)`
- **为什么不同**：套餐是「多商品组合 + 按日期维度」的库存，套餐订单本身不保存全部库存 key 信息，必须依赖下单时存入 Redis 的 `cancel:data` 上下文才能知道要恢复哪些 key。

#### ③ `restoreHotelStock`（酒店）

- Redis：调 `hotelPurchaseService.refundHotel`，按 `checkInDate ~ checkOutDate` 区间恢复
- DB：用 `generateNights` 生成入住每一晚，对每一晚 `RoomInventory.increment({ availableStock: +roomCount, soldStock: -roomCount })`
- **为什么不同**：酒店库存按「房型 × 日期」二维维度存储，每个 `RoomInventory` 行是「房型 + 某一天」，退款时要把入住期间每一晚都加回去。

#### ④ `restoreParkingStock`（停车）

- DB：`Parking.increment("availableCount", { by: 1 })` —— 固定 +1
- Redis：`del parking:pay:expire:${orderNumber}`（清理支付过期定时 key）
- ⚠️ **注意**：停车场**没有 Redis 库存**。车位（`availableCount`）只存在 DB 的 `Parking` 表里。Redis 里只有两个临时 key：
  - `parking:lock:${parkingId}`：下单瞬间的分布式锁（防超卖），用完即释放
  - `parking:pay:expire:${orderNo}`：10 分钟支付超时标记（TTL 10min），不是库存
- **为什么不同**：停车是「单停车位单维度」模型（一个停车场只有一个总数 `availableCount`，没有日期维度、没有商品组合），DB 事务（`where availableCount > 0`）+ Redis 分布式锁已足够防超卖，不需要再维护一份 Redis 库存镜像。所以退款时只需 DB +1 + 清理过期标记。

### 1.2 总结：差异本质

```
库存模型  →  数据结构  →  key 规则  →  恢复步骤
   ↓           ↓           ↓           ↓
 票务: 单品数量        | 单 key + 选座 + 购买记录
 套餐: 多商品组合×日期  | 依赖 cancel:data 还原上下文
 酒店: 房型×日期二维    | 每晚一行 RoomInventory
 停车: 单车位固定 1    | 固定 +1 + 过期 key
```

每个业务的「库存怎么存」决定「退款怎么恢复」，因此四个函数天然不可合并。

## 二、退款流程（`exports.refund`，L450-590）

退款接口采用 **事务 + 策略模式**，主体逻辑与业务无关，业务差异全部下沉到 `refundHandlers` 注册表。

### 2.1 11 步流程

| 步骤 | 行号     | 操作                                     | 说明                                                                                                     |
| ---- | -------- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 0    | L452     | `sequelize.transaction()`                | 开启事务，保证退款原子性                                                                                 |
| 1    | L467-470 | 参数校验                                 | `orderNumber` 必填，否则 fail                                                                            |
| 2    | L472-486 | 验证操作者身份                           | `userID`(用户) 或 `adminId`(管理员) 至少一个；查 `Member` 或 `User` 表，取 `operatorName`                |
| 3    | L488-498 | **遍历 `refundHandlers` 注册表查找订单** | 见下文第三节                                                                                             |
| 4    | L505-510 | 检查订单状态                             | `order[handler.statusField]` 必须在 `handler.refundableStatuses` 内（一般是 `[2,4]`：已支付/已完成）     |
| 5    | L512-522 | 计算退款金额                             | 调 `handler.calcRefund(order, {forceRefund, reason})`；酒店返回 `canRefund:false` 时直接终止             |
| 6    | L524-532 | 调支付宝退款                             | `util.generateOrderNo('RFD')` 生成退款单号 → `paymentService.refund(...)`                                |
| 7    | L536-541 | 支付宝失败处理                           | `code !== '10000'` 时回滚事务并返回 fail                                                                 |
| 8    | L543-544 | 更新订单状态                             | 调 `handler.updateRefunded(orderNumber, refundAmount, transaction)`（一般是 `status=5, verifyStatus=3`） |
| 9    | L546-564 | 创建退款记录                             | `RefundOrder.create(...)`，附加字段来自 `handler.getRefundRecordExtras(order)`                           |
| 10   | L567     | `transaction.commit()`                   | 提交事务                                                                                                 |
| 11   | L569-572 | 异步恢复库存                             | `handler.restoreStock(order, orderNumber).catch(...)`，**失败不影响退款结果**                            |

### 2.2 关键设计点

1. **事务边界**：步骤 3-9 全部在事务内，支付宝退款失败、订单状态检查失败都会 rollback。
2. **库存恢复放在事务外**：步骤 11 用 `.catch()` 兜底，即使库存恢复失败，退款本身已成功（钱已退给用户），不能因为库存问题影响退款结果。
3. **强制退款**：`forceRefund:true` + `reason` 走酒店分支时跳过阶梯扣款，全额退，并标记 `refundType:2`。
4. **退款类型 `refundType`**：`1`=正常退款，`2`=强制退款。
5. **审核时间 `auditTime`**：用户自助退款(`userID`)为 `null`（待审核），后台操作(`adminId`)为当前时间。

### 2.3 退款金额规则

| 业务 | 退款规则                         |
| ---- | -------------------------------- |
| 票务 | 全额退款，无扣款                 |
| 套餐 | 全额退款，无扣款                 |
| 酒店 | 阶梯退款（见下表），支持强制退款 |
| 停车 | 全额退款，无扣款                 |

**酒店阶梯规则**（`calcHotelRefundAmount`，[L158](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/routes/managementSystem/publicInterface/publicInterface.js#L158>)）：

| 入住前天数 | 退款比例 | 扣款比例 | 规则描述                   |
| ---------- | -------- | -------- | -------------------------- |
| ≥5 天      | 100%     | 0%       | 免费取消                   |
| =4 天      | 70%      | 30%      | 入住前4天-扣30%            |
| =3 天      | 50%      | 50%      | 入住前3天-扣50%            |
| =2 天      | 20%      | 80%      | 入住前2天-扣80%            |
| ≤1 天      | 0%       | 100%     | 不可普通退款（需强制退款） |

## 三、`refundHandlers` 注册表是什么？

「遍历 `refundHandlers` 注册表查找订单（自动适配各业务表）」——这句话指的是 [L303-431](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/routes/managementSystem/publicInterface/publicInterface.js#L303-431>) 定义的一个 JS 对象，它是 **策略模式** 的注册表。

### 3.1 注册表结构

```js
const refundHandlers = {
    ticket:  { orderType:1, model:Order,              ... },
    package: { orderType:2, model:PackageOrderDetail,  ... },
    hotel:   { orderType:3, model:HotelOrder,          ... },
    parking: { orderType:4, model:ParkingReservation,  ... },
    // summerCamp: { orderType:5, ... }   // 预留
};
```

每个 handler 包含 9 个字段：

| 字段                    | 含义                             | 示例（票务）             |
| ----------------------- | -------------------------------- | ------------------------ |
| `orderType`             | 业务类型编号（写入 RefundOrder） | `1`                      |
| `model`                 | 该业务的订单 Sequelize Model     | `Order`                  |
| `statusField`           | 订单状态字段名                   | `'orderStatus'`          |
| `refundableStatuses`    | 可退款的状态值数组               | `[2,4]`                  |
| `amountField`           | 金额字段名                       | `'orderAmount'`          |
| `calcRefund`            | 退款金额计算函数                 | 票务全额退 / 酒店阶梯退  |
| `updateRefunded`        | 退款后更新订单状态的函数         | 设为 `status=5`          |
| `restoreStock`          | 库存恢复函数                     | 4 个 restore\*Stock 之一 |
| `getRefundRecordExtras` | RefundOrder 附加字段提取         | `ticketId`、`ticketName` |

### 3.2 「遍历注册表查找订单」具体在做什么？

对应代码 [L491-498](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/routes/managementSystem/publicInterface/publicInterface.js#L491-498>)：

```js
for (const [type, handler] of Object.entries(refundHandlers)) {
  order = await handler.model.findOne({ where: { orderNumber }, transaction });
  if (order) {
    matchedHandler = handler;
    break;
  }
}
```

**含义**：

1. 退款接口只接收一个 `orderNumber`，**不知道**这个订单号属于哪个业务（票务？酒店？套餐？停车？）。
2. 于是遍历注册表里所有业务的 `model`（Order、PackageOrderDetail、HotelOrder、ParkingReservation），用同一个 `orderNumber` 去各自表里 `findOne`。
3. **第一个查到订单的那个表，就是该订单号所属业务**，对应的 `handler` 就是后续要用的策略。
4. 一旦匹配到，`break` 退出循环，后面业务的查询不再执行。

**「自动适配各业务表」** = 不需要前端传 `orderType` 字段告诉后端这是哪种订单，后端自己挨个表查一遍，查到哪个就是哪个。

### 3.3 这种设计的好处

- **开闭原则**：新增业务（比如注释里预留的 `summerCamp` 夏令）只需要：
  1. 创建对应订单 Model
  2. 实现 `calcRefund` 和 `restoreStock`
  3. 在 `refundHandlers` 里加一项配置
- **refund 主体逻辑完全不用改**：步骤 1-11 的流程对所有业务通用，差异都封装在 handler 里。

### 3.4 注意事项

- 遍历顺序 = `Object.entries` 返回顺序（ES2015 后是插入顺序）。当前顺序：`ticket → package → hotel → parking`。
- 各业务订单号生成时已用不同前缀（如 `T`/`P`/`H` 等），实际不会跨表撞号；遍历只是兜底识别机制。
- 遍历查找有 N 次查询（N=业务数），若业务很多可改为按订单号前缀直接定位单表。

## 四、整体调用链路图

```
前端 POST /api/public/refund
        │  body: { orderNumber, userID?, adminId?, forceRefund?, reason? }
        ▼
exports.refund
        │
        ├─ 1. 校验 orderNumber
        ├─ 2. 验证 userID / adminId → operatorName
        ├─ 3. for (refundHandlers) → matchedHandler + order  ◄── 策略模式匹配
        ├─ 4. 检查 status ∈ refundableStatuses
        ├─ 5. matchedHandler.calcRefund(order, ...) → refundAmount
        ├─ 6. paymentService.refund() → 支付宝
        ├─ 7. 支付宝 code !== '10000' → rollback + fail
        ├─ 8. matchedHandler.updateRefunded(orderNumber, refundAmount, tx)
        ├─ 9. RefundOrder.create(...)
        ├─ 10. transaction.commit()
        └─ 11. matchedHandler.restoreStock(order, orderNumber).catch()
                      │
                      ├── restoreTicketStock   (Redis + Ticket + 购买记录 + 选座)
                      ├── restorePackageStock  (cancel:data + 双 key 按日期)
                      ├── restoreHotelStock    (refundHotel + RoomInventory 每晚)
                      └── restoreParkingStock  (Parking +1 + 过期 key)
```
