# 高并发抢票系统技术文档

## 一、系统概述

### 1.1 业务场景

本系统是一个支持高并发（2万人同时抢购）的票务系统，支持两种票务类型：

- **无需选座**：景区大门门票，只扣库存，不选位置
- **需要选座**：室内剧场/影院，实时选座 + 扣库存（类似大麦/猫眼模式）

### 1.2 核心指标

- **并发能力**：支持2万人同时抢购
- **响应时间**：订单创建 < 10ms
- **数据一致性**：库存扣减原子性，防止超卖
- **可用性**：99.9%（通过Redis连接池、消息队列、补偿机制保证）

## 三、关键技术详解

### 3.1 Redis连接池（核心优化）

#### 3.1.1 为什么需要连接池？

**传统方式的问题：**

```javascript
// 传统方式：每次请求创建新连接
const client = redis.createClient();
await client.connect();
const result = await client.get("key");
await client.quit(); // 频繁创建/销毁连接，性能差
```

**连接池的优势：**

```javascript
// 连接池方式：复用连接
const client = await pool.getClient(); // 从池中获取
const result = await client.get("key");
await pool.releaseClient(client); // 归还到池中
```

#### 3.1.2 连接池配置

```javascript
// 连接池大小：50个连接
const pool = new RedisPool(config, 50);

// 特性：
// 1. 并行初始化：启动时创建50个连接
// 2. 等待队列：连接不足时排队等待
// 3. 健康检查：自动检测连接状态
// 4. 故障恢复：连接断开自动重连
```

**性能对比：**
| 指标 | 传统方式 | 连接池方式 | 提升 |
|------|----------|------------|------|
| 连接创建时间 | 5-10ms | 0ms（复用） | ∞ |
| 并发处理能力 | 100 QPS | 10,000+ QPS | 100倍 |
| 内存占用 | 高（频繁GC） | 低（稳定） | 80%↓ |

### 3.2 Lua脚本原子操作（核心优化）

#### 3.2.1 为什么需要Lua脚本？

**传统分布式锁的问题：**

```javascript
// 传统方式：分布式锁
const lock = await redisService.acquireLock("ticket:lock:100");
if (lock) {
  try {
    const stock = await redis.get("ticket:stock:100");
    if (stock > 0) {
      await redis.decr("ticket:stock:100"); // 第2步
      // 问题：两步之间可能被其他请求插入，导致超卖
    }
  } finally {
    await redisService.releaseLock("ticket:lock:100");
  }
}
```

**Lua脚本的优势：**

```lua
-- Lua脚本：原子执行
local stock = redis.call('GET', KEYS[1])
if tonumber(stock) > 0 then
    redis.call('DECR', KEYS[1])  -- 检查和扣减在一个原子操作中
    return {success = true}
end
return {success = false}
```

#### 3.2.2 Lua脚本列表

| 脚本                           | 用途         | 关键操作                         |
| ------------------------------ | ------------ | -------------------------------- |
| `ticket_purchase.lua`          | 普通抢票     | 检查库存、扣减、记录购买         |
| `ticket_purchase_seat.lua`     | 选座抢票     | 验证座位、批量续期、创建订单关联 |
| `seat_realtime_lock.lua`       | 实时锁座     | 检查座位状态、锁定、更新用户缓存 |
| `seat_unlock_single.lua`       | 取消单个座位 | 验证用户、释放座位、更新缓存     |
| `seat_validate_and_extend.lua` | 验证并续期   | 检查所有座位、延长到10分钟       |
| `seat_release_all.lua`         | 释放所有座位 | 批量释放、清理缓存               |
| `seat_confirm.lua`             | 确认售出     | 更新座位状态为已售               |

**性能对比：**
| 指标 | 分布式锁 | Lua脚本 | 提升 |
|------|----------|---------|------|
| 执行时间 | 10-20ms | 1-5ms | 3-5倍 |
| 并发冲突 | 高（锁竞争） | 无（单线程队列） | 彻底解决 |
| 代码复杂度 | 高（锁管理） | 低（原子操作） | 简化70% |
| 2万并发成功率 | 85% | 99.9% | 显著提升 |

### 3.3 消息队列异步处理（核心优化）

#### 3.3.1 为什么需要消息队列？

**同步处理的问题：**

```javascript
// 同步处理：用户等待所有操作完成
app.post('/createOrder', async (req, res) => {
    // 1. 扣减Redis库存（5ms）
    await redis.decr('stock');

    // 2. 写入数据库（50ms）
    await Order.create({...});

    // 3. 同步库存到数据库（30ms）
    await Ticket.update({...});

    // 用户等待：85ms
    res.json({success: true});
});
```

**异步处理的优势：**

```javascript
// 异步处理：只操作Redis，立即返回
app.post('/createOrder', async (req, res) => {
    // 1. 扣减Redis库存（5ms）
    await redis.decr('stock');

    // 2. 发送消息到队列（1ms）
    await queue.add({type: 'createOrder', data: {...}});

    // 用户等待：6ms
    res.json({success: true});
});

// 工作进程异步处理队列
queue.process(async (job) => {
    await Order.create(job.data);  // 后台处理
});
```

#### 3.3.2 队列设计

| 队列             | 用途     | 并发策略              | 重试机制      |
| ---------------- | -------- | --------------------- | ------------- |
| `orderQueue`     | 订单创建 | 每秒1000个            | 3次，指数退避 |
| `stockSyncQueue` | 库存同步 | 批量处理（5秒/100条） | 5次，固定延迟 |
| `paymentQueue`   | 支付回调 | 顺序处理              | 3次，指数退避 |
| `cancelQueue`    | 订单取消 | 延迟执行（10分钟）    | 3次           |

**性能对比：**
| 指标 | 同步处理 | 异步处理 | 提升 |
|------|----------|----------|------|
| 接口响应时间 | 80-100ms | 5-10ms | 10倍 |
| 并发处理能力 | 100 QPS | 10,000+ QPS | 100倍 |
| 数据库压力 | 高 | 低（批量处理） | 90%↓ |
| 用户体验 | 差（等待久） | 好（立即响应） | 显著提升 |

### 3.4 选座功能实现（新增功能）

#### 3.4.1 实时锁座模式

**流程：**

```
0秒    用户点击座位A → 后端锁座3分钟
30秒   用户点击座位B → 后端锁座3分钟
60秒   用户点击座位C → 后端锁座3分钟

用户点击下单 → 验证所有座位（剩余时间>30秒）
            → 创建订单，所有座位延长到10分钟
```

**Redis数据结构：**

```
# 座位实时状态 Hash
Key: seat:status:{ticketId}
Field: {row}:{col}  如 "5:8"
Value: {
    "status": 2,        // 1-空闲, 2-锁定, 3-已售
    "userId": 123,     // 锁定用户ID
    "seatNo": "5排8座",
    "lockTime": 1744252800000,
    "expireTime": 1744252980000
}

# 用户已选座位缓存
Key: user:seat:{userId}:{ticketId}
Value: [{"row":5,"col":8}, {"row":5,"col":9}]
Expire: 180 (3分钟)

# 订单座位关联
Key: order:seat:{orderNo}
Value: {
    "ticketId": 100,
    "seats": ["5:8", "5:9"],
    "userId": 123,
    "status": 2
}
Expire: 600 (10分钟)
```

#### 3.4.2 补偿机制（解决幽灵座位）

**问题场景：**

```
更新MySQL订单状态 = 取消
    ↓
释放Redis座位 = 失败（网络超时）
    ↓
结果：MySQL已取消，Redis座位仍被锁定（幽灵座位）
```

**解决方案：**

```javascript
// 1. 创建补偿任务（数据库事务中）
await CompensationTask.create({
  type: "seat_release",
  orderNo: orderNo,
  ticketId: ticketId,
  userId: userId,
  status: "pending",
  retryCount: 0,
  maxRetry: 5,
});

// 2. 立即尝试释放座位
await ticketPurchaseService.releaseAllSeats({ ticketId, userId });

// 3. 定时任务兜底（每30秒检查）
cron.schedule("*/30 * * * * *", async () => {
  const tasks = await CompensationTask.findAll({
    where: { status: "pending", retryCount: { [Op.lt]: 5 } },
  });
  for (const task of tasks) {
    await releaseSeatsAsync(task);
  }
});

// 4. 最终兜底：座位有过期时间（3分钟/10分钟）
// 即使补偿任务失败，座位也会自动过期释放
```

### 建议实现方案

如需实现订单状态实时推送，可考虑以下方案：

1. **WebSocket方案** (推荐)
   - 使用 `socket.io` 或原生 `ws` 库
   - 订单状态变更时主动推送给客户端
   - 减少不必要的轮询请求

2. **SSE (Server-Sent Events)**
   - 单向推送，实现简单
   - 适合订单状态更新场景

3. **长轮询 (Long Polling)**
   - 兼容性好，无需额外协议
   - 但仍有延迟和服务器压力
