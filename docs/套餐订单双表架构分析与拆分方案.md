### 1.3 数据写入时序

```
购买套餐请求
    │
    ├─ combo.js buyCombo()
    │   ├─ 扣减 Redis 库存
    │   ├─ 构建订单数据
    │   └─ 发送 MQ 消息
    │
    └─ orderWorker.js processPackageOrder()
        ├─ ① Order.create()         ← 写入 orders 表（主订单）

```

**关键点**：必须先写入 `orders` 表，再写入 `package_order_details` 表，否则外键约束会报错。

## 二、为什么要做关联？设计意图是什么？

### 2.1 原始设计意图

`orders` 表最初是为**票务订单**设计的，存储了票务相关的所有信息。当后来增加套餐功能时，采用了**主从表模式**：

```
orders（主表）
  ├── 票务订单：所有信息都在这一张表里
  └── 套餐订单：只存公共字段（订单号、用户、金额、状态、支付信息）
        └── package_order_details（从表）：存套餐特有字段（房型、门票、核销码等）
```

这种设计的意图是：

1. **统一支付入口**：支付宝回调只需要查 `orders` 表，不用区分订单类型
2. **统一退款入口**：退款流程只需要操作 `orders` 表
3. **统一订单列表**：后台管理可以查一张表看到所有订单

### 2.2 实际带来的问题

| 问题                  | 说明                                                                                                               |
| --------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **外键约束报错**      | 套餐订单必须先写 `orders` 再写 `package_order_details`，顺序错了就报错（这就是之前 Bug-1 的根因）                  |
| **orders 表字段冗余** | 套餐订单不需要 `ticketType`、`ticketPrice`、`userIdCard`、`playDate`、`seat` 等字段，但必须传值（之前是 NOT NULL） |
| **查询复杂**          | 查套餐订单需要 JOIN 两张表，票务订单只查一张表                                                                     |
| **状态同步风险**      | `orders` 和 `package_order_details` 都有 `verifyStatus`，需要保持一致                                              |
| **支付回调耦合**      | 支付回调只更新 `orders` 表，套餐订单的核销状态需要额外处理                                                         |
| **退款逻辑不通用**    | 退款只处理票务库存恢复，套餐库存恢复需要单独写逻辑                                                                 |

### 3.2 核心依赖：支付系统

**`orders` 表最大的依赖是支付宝支付系统**：

```
支付宝支付流程：
  创建订单 → orderNumber 作为 out_trade_no 传给支付宝
  支付宝回调 → 用 out_trade_no 查 orders 表 → 更新支付状态

支付宝退款流程：
  退款请求 → 用 orderNumber 查 orders 表 → 获取 alipayTradeNo → 调用支付宝退款
  退款成功 → 更新 orders 表状态 → 创建 RefundOrder
```

## 四、能不能只要 `package_order_details` 一张表？

### 4.1 直接回答：不能简单去掉，但可以改造

如果直接去掉 `orders` 表中套餐订单的记录，会导致以下问题全部爆出：

| 问题                       | 影响                                                                |
| -------------------------- | ------------------------------------------------------------------- |
| 支付宝回调找不到订单       | `Order.findOne({ where: { orderNumber: out_trade_no } })` 返回 null |
| 退款流程无法执行           | 退款需要 `order.alipayTradeNo` 和 `order.orderAmount`               |
| 退款单外键约束失败         | `RefundOrder.orderNo` 引用 `orders.orderNumber`                     |
| 后台订单列表查不到套餐订单 | `Order.findAll()` 只能查到票务订单                                  |
| 超时取消无法判断订单状态   | `Order.findOne()` 返回 null，无法判断是否已支付                     |
| 支付关闭无法恢复库存       | `order.goodsId` 和 `order.buyNum` 为空                              |

## 五、方案 A：让 `package_order_details` 自包含（推荐）

**核心思路**：将套餐订单需要的公共字段（支付信息、用户信息、订单状态等）从 `orders` 表复制到 `package_order_details` 表，使其成为一张完全独立的表，不再依赖 `orders` 表。

### 5.1 改造后的 `package_order_details` 表结构

```sql

ALTER TABLE package_order_details ADD COLUMN userPhone VARCHAR(20) COMMENT '用户电话';
ALTER TABLE package_order_details ADD COLUMN orderStatus INT DEFAULT 1 COMMENT '订单状态：1-待支付 2-待核销 3-已取消 4-已完成 5-已退款';
ALTER TABLE package_order_details ADD COLUMN orderAmount DECIMAL(10,2) DEFAULT 0 COMMENT '订单金额';
ALTER TABLE package_order_details ADD COLUMN refundAmount DECIMAL(10,2) DEFAULT 0 COMMENT '退款金额';
ALTER TABLE package_order_details ADD COLUMN alipayTradeNo VARCHAR(64) COMMENT '支付宝交易号';

```

### 5.3 方案 A 优缺点

| 优点                                 | 缺点                                              |
| ------------------------------------ | ------------------------------------------------- |
| 套餐订单完全独立，不再受外键约束困扰 | 修改文件多（7+个文件）                            |
| 套餐订单字段自包含，查询不需要 JOIN  | 支付/退款逻辑需要增加订单类型判断                 |
| 套餐和票务彻底解耦，互不影响         | `orderStatus`、`alipayTradeNo` 等字段在两表中冗余 |
| 后续套餐功能扩展不受 orders 表限制   | 需要数据迁移                                      |
| 不需要往 orders 表塞不相关的字段     | 后台订单列表需要查两张表合并                      |

## 六、方案 B：保持现状，优化 orders 表为通用订单基表

**核心思路**：保留 `orders` 表作为通用订单基表，但将其改造为只存真正通用的字段，票务特有字段移到 `ticket_order_details` 表（与 `package_order_details` 对称）。

### 6.1 改造后的结构

```
orders（通用订单基表 - 只存公共字段）
  ├── orderNumber    订单号
  ├── orderType      订单类型（1=票务 2=套餐）
  ├── memberId       用户ID
  ├── userName       用户姓名
  ├── userPhone      用户电话
  ├── buyNum         购买数量
  ├── orderStatus    订单状态
  ├── orderAmount    订单金额
  ├── refundAmount   退款金额
  ├── alipayTradeNo  支付宝交易号
  └── paymentTime    支付时间

ticket_order_details（票务订单详情 - 新建）
  ├── orderNumber    FK → orders.orderNumber
  ├── ticketType     票种
  ├── ticketPrice    票价
  ├── goodsId        商品ID
  ├── userIdCard     身份证号
  ├── playDate       游玩日期
  ├── seat           座位
  └── verifyStatus   核销状态

package_order_details（套餐订单详情 - 保持不变）
  ├── orderNumber    FK → orders.orderNumber
  ├── packageId      套餐ID
  ├── groupId        分组ID
  ├── itemType       子项类型
  ├── ...            其他套餐字段
  └── verifyCode     核销码
```

### 6.2 方案 B 优缺点

| 优点                        | 缺点                               |
| --------------------------- | ---------------------------------- |
| 支付/退款逻辑不需要改       | 仍然有外键约束                     |
| 后台订单列表只查一张表      | 需要新建 `ticket_order_details` 表 |
| orders 表干净，只有公共字段 | 票务订单需要迁移数据               |
| 两种订单结构对称，易于理解  | 改动量比方案 A 更大                |

## 七、方案对比与推荐

| 维度          | 方案 A（套餐独立） | 方案 B（通用基表） | 当前方案（双表关联） |
| ------------- | ------------------ | ------------------ | -------------------- |
| 改动量        | 中等（7+文件）     | 大（10+文件）      | 无                   |

| 数据冗余      | 状态/支付字段冗余  | 无冗余             | orders 表字段冗余    |

### 🏆 推荐：方案 A（套餐独立）

理由：

1. **解决根本问题**：彻底消除外键约束带来的麻烦
2. **改动量可控**：比方案 B 小
3. **扩展性好**：未来新增订单类型（如酒店直订、活动报名）不受 orders 表限制
4. **符合业务逻辑**：套餐和票务是两种完全不同的业务，数据结构差异大，分开更合理

### 9.3 核心变更详解

#### 变更1：PackageOrderDetail 自包含

`package_order_details` 表新增了以下独立字段，不再依赖 `orders` 表：

```
新增字段：
├── userId        INT       用户ID
├── userName      STRING    用户姓名
├── userPhone     STRING    用户电话
├── buyNum        INT       购买数量
├── orderStatus   INT       订单状态（1-待支付 2-待核销 3-已取消 4-已完成 5-已退款）
├── orderAmount   DECIMAL   订单金额
├── refundAmount  DECIMAL   退款金额
├── alipayTradeNo STRING    支付宝交易号
└── paymentTime   DATE      支付时间
```

#### 变更2：订单创建流程

```
修改前：
  processPackageOrder()
    ├── ① Order.create()              ← 写入 orders 表
    └── ② PackageOrderDetail.create() ← 写入 package_order_details 表

修改后：
  processPackageOrder()
    └── ① PackageOrderDetail.create() ← 只写一张表，包含所有信息
```

#### 变更3：支付回调流程

```
修改前：
  processPaymentCallback()
    └── Order.findOne() → Order.update()  ← 只查 orders 表

修改后：
  processPaymentCallback()
    ├── Order.findOne()                    ← 先查票务订单
    └── PackageOrderDetail.findOne()       ← 没找到则查套餐订单
        ├── 票务订单 → Order.update()
        └── 套餐订单 → PackageOrderDetail.update()
```

#### 变更4：退款流程

```
修改前：
  refund()
    └── Order.findOne() → Order.update() → restoreStockAfterRefund()

修改后：
  refund()
    ├── Order.findOne()                    ← 先查票务订单
    └── PackageOrderDetail.findOne()       ← 没找到则查套餐订单
        ├── 票务订单 → Order.update() + restoreStockAfterRefund()
        └── 套餐订单 → PackageOrderDetail.update() + restorePackageStockAfterRefund()
```

#### 变更5：订单取消流程

```
修改前：
  processOrderCancel()
    └── Order.findOne() → 判断 packageItemId → Order.update()

修改后：
  processOrderCancel()
    ├── Order.findOne()                    ← 先查票务订单
    └── PackageOrderDetail.findOne()       ← 没找到则查套餐订单
        ├── 票务订单 → Order.update() + 恢复票务库存
        └── 套餐订单 → PackageOrderDetail.update() + 恢复套餐库存
```

### 9.4 数据库迁移步骤

迁移文件 `20260530000000-decouple-package-order-details.js` 执行以下操作：

1. **新增字段**：向 `package_order_details` 表添加 9 个新字段
2. **迁移数据**：从 `orders` 表同步套餐订单的公共字段到 `package_order_details`
3. **删除外键**：删除 `package_order_details` 和 `refund_orders` 表上的外键约束
4. **清理数据**：删除 `orders` 表中 `orderType=2` 的套餐订单记录
5. **删除列**：删除 `orders` 表的 `orderType` 列
6. **修正约束**：将新字段从 `allowNull: true` 改为 `allowNull: false`

### 9.5 后续扩展指引

当未来需要新增酒店订单或其他订单类型时，按照以下模式操作：
