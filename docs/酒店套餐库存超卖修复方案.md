## 一、问题清单

### 问题 1：房型库存按 `roomPackageId` 存储，导致超卖 N 倍（P0）

**现象**：一个房型 100 间房，挂 3 个套餐，可售总量变成 300，超卖 2 倍。

**根因**：

`RoomDatePrice`（`room_date_prices`）的库存字段挂在 `roomPackageId + date` 上：

- [roomDatePrice.js#L12-L52](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/models/hotelModel/roomDatePrice.js#L12-L52>)

```
roomPackageId → references room_packages.id
stock / soldStock / availableStock  全部按 roomPackageId 存
```

但物理房间是 `RoomType.stock` 共享的（[roomType.js#L23-L27](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/models/hotelModel/roomType.js#L23-L27>)）。一个房型下 N 个套餐，每个套餐各存一份完整房型库存。

**坐实代码**：[hotel.js#L317-L347](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/routes/managementSystem/hotelRouter/hotel.js#L317-L347>) `setDatePrice`：

```js
let priceData = { stock: combo.roomType.stock, ... }   // 读房型库存=100
const records = DatePriceList.map(item => ({
    roomPackageId: item.id,                             // 每个套餐各存一份
    stock: item.stock || 0,                             // 100
    availableStock: item.availableStock || item.stock || 0, // 100
}));
```

结果：3 个套餐 × 100 = 300 可售，实际 100 间 → 超卖。

`updateRoomTypeStock`（[hotel.js#L420-L478](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/routes/managementSystem/hotelRouter/hotel.js#L420-L478>)）改房型库存时给每个套餐都写相同新值，仍各自独立，且各套餐 `soldStock` 独立累计、互不感知。

### 问题 2：套餐侧库存来源错位 + 关联查错字段（P0）

**2a. 初始化房型库存取数来源错位**

[combo.js#L426-L448](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/routes/managementSystem/comboRouter/combo.js#L426-L448>)：

```js
const hotelStockKey = `hotel:roomtype:stock:${roomType.id}:${date}`; // key 按 roomTypeId（对）
const roomDatePrice = await RoomDatePrice.findOne({
  where: { roomPackageId: roomPackage.id, date: date }, // 数据源按 roomPackageId（错）
});
const stock = roomDatePrice
  ? roomDatePrice.availableStock || roomType.stock
  : roomType.stock;
```

Redis key 是按 `roomTypeId` 共享的，但取数来源是"该套餐对应的那条 RoomDatePrice"，而那条的 `availableStock` 是该套餐独享副本，不含其他套餐已售数。第一个初始化的套餐决定缓存值，后续套餐看到 key 已存在就跳过 → 房型可售数认知不一致。

**2b. `createTicketPriceRule` 查 RoomType 用错字段**

[combo.js#L180](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/routes/managementSystem/comboRouter/combo.js#L180>)：

```js

```

`comboState.roomPackageId` 指向 `room_packages.id`，却拿来查 `room_types.id`。应先查 `RoomPackage` 取 `roomTypeId`，再查 `RoomType`。当前能"通过"仅因自增主键偶发撞上。

**2c. 套餐库存与房型库存是两套独立计数**

[comboPurchaseService.js#L36-L42](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/services/comboPurchaseService.js#L36-L42>) 传两个 key 给 Lua：

- `combo:stock:${packageItemId}:${date}` —— 套餐自己的库存（来自 `PackageDatePrice`，值是 `maxSaleNum`）
- `hotel:roomtype:stock:${roomTypeId}:${date}` —— 房型库存（来自 `RoomDatePrice`，来源错位）

`PackageDatePrice` 的库存是套餐方自己设的 `maxSaleNum`，和房型真实库存不是同一份；房型库存因问题 1 又被复制成 N 份。两套都不可信。

### 问题 4：DB 的 soldStock 从不同步，是脏数据（P1）

## 二、关于抽 `roomInventory` 做公共库存的评估

**结论：方向完全正确，但当前 `roomInventory.js` 需要改造后才能用。**

### 为什么这个方向对

物理房间是 `RoomType` 级别的共享资源，同一房型的所有套餐卖的都是同一批房间。库存的"唯一真源"必须落在 `roomTypeId + date` 维度，而不是 `roomPackageId + date`。抽一张 `roomInventory` 表专门管房型每日库存，是业界标准做法（OTA/酒店系统普遍如此）。

### 当前 `roomInventory.js` 的问题与改造点

当前定义见 [roomInventory.js](<file:///c:/Users/Administrator/Desktop/node-mysql%20-%20副本%20(2)/mynode/node-full-stack/models/hotelModel/roomInventory.js>)：

| 项               | 现状                                       | 问题                                                                                             | 改造                                           |
| ---------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------ | ---------------------------------------------- |
| `roomId`         | 指向 `room_types.id`                       | 字段名歧义，全项目其他地方都用 `roomTypeId`                                                      | 改名 `roomTypeId`，保持一致                    |
| `date`           | `DataTypes.DATE`                           | 带时分秒，与 `RoomDatePrice.date`（`DATEONLY`）不对齐， joins/比较会出问题                       | 改 `DATEONLY`                                  |
| `price`          | `DECIMAL`                                  | **应删除**。价格按套餐不同（同房型 3 个套餐 3 个价），库存按房型共享，二者维度不同，不能放一张表 | 删除 `price` 字段，价格留在 `RoomDatePrice`    |
| 唯一约束         | 无                                         | 同一 `roomTypeId + date` 可能插入多条                                                            | 加 `unique: true` 索引 `(roomTypeId, date)`    |
| `stock`          | 有                                         | 保留，表示该日总库存（容量）                                                                     | 保留                                           |
| `soldStock`      | 有                                         | 保留，该日已售（所有套餐共用）                                                                   | 保留                                           |
| `availableStock` | 有                                         | 保留，`= stock - soldStock`                                                                      | 保留，可由触发器/应用层维护                    |
| 关联注册         | 未在 `associations.js` / `Summary.js` 注册 | 模型没挂载，路由也引不到                                                                         | 补注册                                         |
| 模型名           | `roomInventory`（单数）                    | 与项目其他表复数命名不一致                                                                       | 建议 `RoomInventory` / 表名 `room_inventories` |

### 职责划分（改后）

| 表                        | 维度                   | 职责                                                         |
| ------------------------- | ---------------------- | ------------------------------------------------------------ |
| `RoomType`                | 房型                   | `stock` 作为基础容量（生成每日库存时的默认值）               |
| `RoomInventory`（新启用） | `roomTypeId + date`    | **房型每日库存唯一真源**：stock / soldStock / availableStock |
| `RoomDatePrice`           | `roomPackageId + date` | **只管价格**，删除 stock / soldStock / availableStock        |
| `RoomPackage`             | 套餐                   | 价格策略、包含内容、日期范围，不管库存                       |
| `PackageDatePrice`        | `packageItemId + date` | 套餐项每日价格 + 套餐自己的 `maxSaleNum` 限量                |

这样：**库存共享（按房型），价格独立（按套餐）**，职责清晰。

### Redis 层

Redis key 维持现状（已经是按 `roomTypeId`）：

- `hotel:roomtype:stock:${roomTypeId}:${date}` —— 唯一运行时权威
- `combo:stock:${packageItemId}:${date}` —— 套餐自己的限量（`maxSaleNum`）

只需把初始化来源从 `RoomDatePrice` 改成 `RoomInventory`。

### 删除 `hotel:stock:${roomPackageId}` 这个 key

`hotelPurchaseService` 里的 `hotel:stock:${roomPackageId}:${date}` 是多余的独立副本，直接删除该 key 及相关扣减逻辑，只保留 `hotel:roomtype:stock:${roomTypeId}:${date}`。

## 五、风险控制与回滚

### 双写过渡期

1. **第一阶段**：`RoomInventory` 建好并写入，但 `RoomDatePrice` 的库存列**暂不删**。扣减层切到 `RoomInventory`，但 `RoomDatePrice` 库存列由同步逻辑继续写（双写），便于对比校验。
2. **第二阶段**（观察 1 周无异常后）：前台/后台读全部切到 `RoomInventory`，`RoomDatePrice` 库存列停止写入。
3. **第三阶段**：删除 `RoomDatePrice` 的 stock/soldStock/availableStock 列 + 删除相关代码。

### 校验手段

- 每日定时任务对账：`RoomInventory.availableStock` vs Redis `hotel:roomtype:stock:*`，不一致告警。
- `RoomInventory.soldStock` == 该房型所有套餐 `PackageOrderDetail` 已支付订单的 `buyNum` 之和。

### 回滚

- 若出现问题，扣减层回退到读 `RoomDatePrice`（列还在），数据未丢失。
- Redis key 维度不变，无需刷 Redis。

## 六、已确认决策（2026-07-12）

1. **`RoomInventory` 按 `(roomTypeId, date)` 唯一，承担每日库存。**

   - 套餐 `PackageDatePrice.availableStock >= num`（套餐当日限量）
