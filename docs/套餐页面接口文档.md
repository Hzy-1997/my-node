# 套餐页面接口文档

> 根据以下后端文件整理：
>
> - `routes/managementSystem/comboRouter/index.js`
> - `routes/managementSystem/comboRouter/combo.js`
> - `models/packageModel/productPackage.js`
> - `models/packageModel/packageItem.js`
> - `models/packageModel/packagePriceRule.js`
> - `models/packageModel/packageDatePrice.js`
> - `models/packageModel/packageOrderDetail.js`

## 1. 基础信息

### 1.1 接口前缀

后端在 `app.js` 中统一挂载：

```js
app.use('/api', indexRouter)
```

套餐路由在 `routes/index.js` 中挂载：

```js
router.use('/package', require('./managementSystem/comboRouter/index.js'))
```

所以套餐管理端接口统一前缀为：

```txt
/api/package
```

### 1.2 当前套餐接口列表

| 功能 | Method | 接口 |
| --- | --- | --- |
| 套餐主表新增/修改/删除 | POST | `/api/package/comboOperation` |
| 套餐主表列表 | GET | `/api/package/comboList` |
| 套餐产品/子项新增/修改/删除 | POST | `/api/package/productOperation` |
| 套餐产品/子项列表 | GET | `/api/package/productList` |
| 创建或更新套餐日历价格规则 | POST | `/api/package/createTicketPriceRule` |
| 购买套餐 | POST | `/api/package/buyCombo` |

### 1.3 统一返回格式

后端使用 `utils/util.js` 的 `success/fail`：

成功：

```json
{
  "code": 200,
  "message": "获取成功",
  "data": {}
}
```

失败：

```json
{
  "code": 401,
  "message": "业务错误信息",
  "data": ""
}
```

前端建议统一按 `code === 200` 判断成功，其余作为业务失败提示 `message`。

### 1.4 鉴权说明

当前 `/api/package` 路由在 `routes/index.js` 中没有加 `checkToken` 中间件；`comboRouter/index.js` 虽然引入了 `checkToken`，但没有实际使用。

如果前端项目统一带 token，也可以照常携带：

```http
Authorization: Bearer <token>
Content-Type: application/json
```

但以当前代码看，套餐接口本身没有强制校验 token。

## 2. 主要枚举

### 2.1 套餐主表 `ProductPackage`

| 字段 | 含义 |
| --- | --- |
| `type` | 套餐类型：`1` 酒店套餐，`2` 游玩套餐，`3` 赛事套餐，`4` 自定义 |
| `saleMode` | 销售方式：`1` 独立售卖，`2` 必须搭配主产品 |
| `status` | 状态：`1` 上架，`2` 下架，`3` 售罄 |

### 2.2 套餐子项 `PackageItem`

| 字段 | 含义 |
| --- | --- |
| `isPrimary` | 是否主产品：`1` 主产品，`0` 附带产品 |
| `itemType` | 子项类型：`1` 酒店房型，`2` 门票，`3` 其他 |
| `useDateType` | 使用日期类型：`1` 跟随主产品入住日期，`2` 跟随主产品游玩日期，`3` 固定日期，`4` 购买后 N 天内 |

### 2.3 价格规则 `ruleConfig`

`ruleConfig` 是 JSON，后端会按日期分为：

| key | 含义 |
| --- | --- |
| `weekday` | 工作日 |
| `weekend` | 周末 |
| `holiday` | 节假日 |

每一项支持：

| 字段 | 含义 |
| --- | --- |
| `priceType` | `1` 固定价格，`2` 百分比上浮，`3` 百分比下降，`4` 原价 |
| `priceValue` | 价格值。固定价格时表示最终价；百分比时表示百分比数字 |

示例：

```json
{
  "weekday": { "priceType": 4, "priceValue": 0 },
  "weekend": { "priceType": 2, "priceValue": 20 },
  "holiday": { "priceType": 1, "priceValue": 699 }
}
```

说明：

- `priceType = 1`：直接使用 `priceValue` 作为当天价格。
- `priceType = 2`：基于 `PackageItem.unitPrice` 上浮百分比。
- `priceType = 3`：基于 `PackageItem.unitPrice` 下降百分比。
- `priceType = 4`：使用 `PackageItem.unitPrice` 原价。

## 4. 接口详情

## 4.1 套餐主表新增/修改/删除

### 接口

```http
POST /api/package/comboOperation
Content-Type: application/json
```

### 功能说明

操作 `product_packages` 套餐主表。通过 `action` 区分新增、修改、删除。

### 请求参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `action` | string | 是 | `create` 新增，`update` 修改，`delete` 删除 |
| `id` | number | 修改/删除必填 | 套餐 ID |
| `name` | string | 新增必填 | 套餐名称 |
| `subTitle` | string | 否 | 副标题 |
| `type` | number | 否 | 套餐类型 |
| `category` | string | 否 | 分类 |
| `coverImage` | string | 否 | 封面图 |
| `bannerImages` | array | 否 | 轮播图 |
| `marketPrice` | number | 否 | 市场价 |
| `minPrice` | number | 否 | 最低价 |
| `maxPrice` | number | 否 | 最高价 |
| `saleMode` | number | 否 | 销售方式 |
| `startDate` | string | 否 | 销售开始日期 |
| `endDate` | string | 否 | 销售结束日期 |
| `tags` | array | 否 | 标签数组 |
| `includes` | string | 否 | 套餐包含权益 |
| `refundRule` | string | 否 | 退订规则 |
| `useRule` | string | 否 | 使用规则 |
| `sortOrder` | number | 否 | 排序 |
| `status` | number | 否 | 状态 |

> 后端直接 `ProductPackage.create(req.body)` 和 `ProductPackage.update(req.body)`，所以 body 里除 `action` 外的字段会一起传入 Sequelize。前端应只传模型中存在的字段，避免无效字段污染请求。

### 新增示例

```json
{
  "action": "create",
  "name": "亲子酒店双人套餐",
  "subTitle": "含一晚住宿和双人早餐",
  "type": 1,
  "category": "hotel",
  "coverImage": "https://example.com/cover.jpg",
  "bannerImages": [
    "https://example.com/banner1.jpg",
    "https://example.com/banner2.jpg"
  ],
  "marketPrice": 999,
  "minPrice": 599,
  "maxPrice": 799,
  "saleMode": 1,
  "startDate": "2026-07-01",
  "endDate": "2026-08-31",
  "tags": ["亲子", "酒店", "早餐"],
  "includes": "豪华大床房 1 晚，双人早餐",
  "refundRule": "入住前 24 小时可退",
  "useRule": "请提前预约",
  "sortOrder": 10,
  "status": 1
}
```

### 修改示例

```json
{
  "action": "update",
  "id": 12,
  "name": "亲子酒店双人套餐",
  "status": 2
}
```

### 删除示例

```json
{
  "action": "delete",
  "id": 12
}
```

### 成功响应

```json
{
  "code": 200,
  "data": "",
  "message": "创建成功"
}
```

可能的成功 message：

- `创建成功`
- `更新成功`
- `删除成功`

### 失败响应

```json
{
  "code": 401,
  "data": "",
  "message": "无效的操作，缺少必要参数"
}
```

可能的失败 message：

- `无效的操作，缺少必要参数`
- `无效的操作或套餐不存在`
- `无效的操作类型`
- `操作失败`

### 前端使用建议

- 套餐主表用于页面顶部的套餐基础信息表单。
- 删除套餐时，`ProductPackage.destroy({ individualHooks: true })`，并且模型关联里套餐和子项是级联删除关系，删除前端应做二次确认。
- 列表刷新建议在新增、修改、删除成功后重新调用 `/comboList`。

## 4.3 套餐产品/子项新增/修改/删除

### 接口

```http
POST /api/package/productOperation
Content-Type: application/json
```

### 功能说明

操作 `package_items` 套餐子项表。通过 `action` 区分新增、修改、删除。

套餐主表和套餐子项的关系：

- 一个套餐主表 `ProductPackage` 可以有多个 `PackageItem`。
- 同一个 `groupId` 下通常应该有 1 个主产品 `isPrimary=1` 和多个附带产品 `isPrimary=0`。
- 购买接口目前主要处理 `itemType=1` 酒店类子项。

### 请求参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `action` | string | 是 | `create` 新增，`update` 修改，`delete` 删除 |
| `id` | number | 修改/删除必填 | 子项 ID |
| `packageId` | number | 新增必填 | 套餐主表 ID |
| `groupId` | number | 新增必填 | 分组 ID |
| `isPrimary` | number | 否 | 是否主产品 |
| `itemType` | number | 否 | 子项类型 |
| `roomPackageId` | number | 酒店类建议必填 | 酒店房型套餐 ID |
| `ticketId` | number | 门票类建议必填 | 门票 ID |
| `ticketPriceRuleId` | number | 否 | 历史/预留字段，当前门票子项不需要传 |
| `startDate` | string | 否 | 销售开始日期 |
| `endDate` | string | 否 | 销售结束日期 |
| `maxSaleNum` | number | 否 | 总限量 |
| `maxBuyNum` | number | 否 | 每单限购 |
| `availableStock` | number | 否 | 可售库存 |
| `itemName` | string | 否 | 显示名称 |
| `quantity` | number | 否 | 包含数量 |
| `unitPrice` | number | 否 | 单价 |
| `useDateType` | number | 否 | 使用日期类型 |
| `useDateOffset` | number | 否 | 日期偏移 |
| `useDateValue` | string | 否 | 固定日期或 N 天 |
| `description` | string | 否 | 子项说明 |
| `icon` | string | 否 | 图标 |
| `sortOrder` | number | 否 | 排序 |

### 成功响应

```json
{
  "code": 200,

```

可能的成功 message：

- `创建成功`

```json
{
  "code": 401,
```

- `无效的操作，缺少必要参数`
- `缺少必要参数`

### 前端使用建议

- 套餐编辑页建议做成：左侧/上方套餐主信息，下面用子项表格管理 `PackageItem`。
- 新增子项前必须先创建套餐主表，拿到 `packageId` 后才能配置子项。
- 当前后端不会校验 `groupId` 下是否只有一个主产品，前端最好做限制。
- 当前后端不会校验 `itemType=1` 时必须传 `roomPackageId`，但后续价格规则和购买流程会依赖该字段。
- `itemType=2` 门票子项当前只需要关联 `ticketId`，不要把 `ticketPriceRuleId` 当成必填项。

## 4.4 套餐产品/子项列表

### 接口

```http
GET /api/package/productList
```

## 4.5 创建或更新套餐日历价格规则

### 接口

```http
POST /api/package/createTicketPriceRule
Content-Type: application/json
```

### 功能说明

给酒店类套餐子项 `PackageItem` 配置价格规则，并生成 `package_date_prices` 日历价格库存。

> 注意：接口名 `/createTicketPriceRule` 是历史命名，当前实现会按酒店房型逻辑处理并依赖 `roomPackageId`。门票子项当前不配置价格规则，也不需要传 `ticketPriceRuleId`。

当前逻辑：

1. 校验 `action`、`packageItemId`、`ruleConfig`。
2. 查询套餐子项 `PackageItem`。
3. 如果该子项已有 `PackagePriceRule`，则更新；否则创建。
4. 根据子项的 `startDate`、`endDate`、`unitPrice`、`maxSaleNum` 和 `ruleConfig` 生成每日价格。
5. 批量写入 `PackageDatePrice`。

### 请求参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `action` | string | 是 | 当前主要使用 `create`。代码也写了 `update`，但实现存在问题，见注意事项 |
| `packageItemId` | number | 是 | 套餐子项 ID |
| `ruleConfig` | object | 是 | 价格规则 JSON |

```json
{
  "action": "create",

    "holiday": { "priceType": 1, "priceValue": 899 }
```
```json
  }
}
```

### 失败响应


可能的失败 message：

- `缺少操作类型`
- `请选择套餐`

- `套餐已下架`
- `房间类型不存在`
- `最大销售数量不能大于库存数量`
- `操作失败,联系管理员`
- `系统错误`

### 前端使用建议

- 这个接口建议放在子项编辑弹窗里的“价格规则”区域。
- 配置前必须确保子项有 `startDate`、`endDate`、`unitPrice`、`maxSaleNum`。
- 价格规则创建成功后，后端会生成日历价，但当前没有日历价查询接口。前端如果需要日历预览，需要后端新增查询 `PackageDatePrice` 的接口。
- `ruleConfig` 建议前端固定为三段配置：工作日、周末、节假日。

### 当前实现注意事项

这个接口目前有几处后端风险，前端联调时容易遇到：

1. 代码用 `comboState.state == 2` 判断下架，但 `PackageItem` 模型没有 `state` 字段，只有套餐主表有 `status` 字段。
2. 代码用 `RoomType.findOne({ id: comboState.roomPackageId })` 查房型，但 `roomPackageId` 实际关联的是 `room_packages.id`，不是 `room_types.id`。
3. `action == "update"` 分支里 `PackagePriceRule.update(req.body)` 没有 `where` 条件，存在更新异常风险。
4. `bulkCreate` 的 `updateOnDuplicate` 字段使用了部分蛇形字段名，和 Sequelize 属性名不完全一致，联调时需要确认是否能正常覆盖旧日历价。

前端开发阶段建议优先使用 `action: "create"` 作为“创建或覆盖规则”的接口。

## 4.6 购买套餐

### 接口

```http
POST /api/package/buyCombo
Content-Type: application/json
```

### 功能说明

创建套餐订单并扣减 Redis 库存。当前代码完整实现的是 `itemType=1` 酒店套餐购买；`itemType=2` 门票套餐分支为空，暂不可用。

处理流程：

1. 校验用户、套餐子项、类型、购买数量、日期。
2. 查询套餐子项和关联的 `roomPackage`。
3. 校验套餐未过期、房型套餐未过期、库存充足。
4. 查询用户 `Member`。
5. 生成订单号，前缀 `ORDPK`。
6. 酒店套餐按入住日期区间逐日扣减套餐库存和酒店房型库存。
7. 把订单数据推入队列异步写库。
8. 创建 10 分钟超时取消任务。
9. 返回订单号和过期时间。

### 请求参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `userId` | number | 是 | 用户 ID，对应 `Member.id` |
| `packageItemId` | number | 是 | 套餐子项 ID |
| `itemType` | number | 是 | `1` 酒店，`2` 门票。当前只有 `1` 完整实现 |
| `num` | number | 是 | 购买数量，当前最大不能超过 5 |
| `startDate` | string | 是 | 使用开始日期/入住日期，`YYYY-MM-DD` |
| `endDate` | string | 是 | 使用结束日期/离店日期，`YYYY-MM-DD` |

> 代码里解构了 `id`，但没有实际使用。

### 请求示例

```json
{
  "userId": 1001,
  "packageItemId": 33,
  "itemType": 1,
  "num": 1,
  "startDate": "2026-07-20",
  "endDate": "2026-07-21"
}
```

### 成功响应

```json
{
  "code": 200,
  "message": "订单创建成功，请尽快支付",
  "data": {
    "orderNo": "ORDPK202607100000011783704000000",
    "expireTime": 1783704600000
  }
}
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `orderNo` | string | 套餐订单号 |
| `expireTime` | number | 支付过期时间戳，当前为创建后 10 分钟 |

### 失败响应

```json
{
  "code": 401,
  "data": "",
  "message": "缺少必要信息"
}
```

可能的失败 message：

- `缺少必要信息`
- `类型错误`
- `最大购买数量不能超过5个`
- `套餐不存在`
- `套餐已过期`
- `房型已过期`
- `暂无库存`
- `时间错误`
- `用户不存在`
- `套餐未关联酒店房型`
- `房间类型不存在`
- `房间类型不可用`
- Redis/Lua 扣库存失败时返回库存服务里的失败 message

### 前端使用建议

- 酒店套餐下单前应让用户选择入住/离店日期，并确保 `startDate <= endDate`。
- 当前后端会按 `generateDateRange(startDate, endDate)` 包含首尾日期逐日扣库存。如果业务上离店日不应扣库存，需要后端调整。
- 下单成功后应进入支付页或支付弹窗，使用返回的 `orderNo`。
- 订单 10 分钟未支付会进入延迟取消任务，前端可用 `expireTime` 做倒计时。
- `num` 前端应限制最大为 5。
- `itemType=2` 现在后端未实现购买逻辑，前端不要开放门票套餐直接购买，除非后端补齐。

## 5. 前端页面开发建议

### 5.1 页面结构

建议套餐管理页面拆成四块：

1. 套餐列表页
   - 调用 `/api/package/comboList`
   - 支持类型、状态、名称筛选
   - 操作：新增、编辑、删除、配置子项

2. 套餐基础信息弹窗/页面
   - 调用 `/api/package/comboOperation`
   - 字段来自 `product_packages`

3. 套餐子项配置页/抽屉
   - 调用 `/api/package/productList` 查询子项
   - 调用 `/api/package/productOperation` 新增/修改/删除子项
   - 注意当前后端缺少 `packageId` 筛选，建议补接口或让后端扩展现有接口

4. 价格规则配置弹窗
   - 调用 `/api/package/createTicketPriceRule`
   - 配置工作日、周末、节假日三套规则

### 5.2 推荐表单校验

套餐主表：

- `name` 必填。
- `type` 必填。
- `marketPrice/minPrice/maxPrice` 不能小于 0。
- `startDate <= endDate`。
- `bannerImages/tags` 使用数组。
- `status` 限定在 `1/2/3`。

套餐子项：

- `packageId` 必填。
- `groupId` 必填。
- `itemType=1` 时 `roomPackageId` 必填。
- `itemType=2` 时 `ticketId` 必填，`ticketPriceRuleId` 不需要传。
- `unitPrice` 不能小于 0。
- `maxSaleNum/maxBuyNum/availableStock` 不能小于 0。
- `maxBuyNum` 如果后端购买接口不改，前端还要限制 `num <= 5`。

价格规则：

- `packageItemId` 必填。
- `ruleConfig.weekday/weekend/holiday` 都建议传。
- `priceType=1` 时 `priceValue` 应大于等于 0。
- `priceType=2/3` 时 `priceValue` 建议在 `0-100` 之间。

### 5.3 前端 API 封装示例

```js
export const packageApi = {
  getComboList(params) {
    return request.get('/api/package/comboList', { params })
  },
  saveCombo(data) {
    return request.post('/api/package/comboOperation', data)
  },
  getProductList(params) {
    return request.get('/api/package/productList', { params })
  },
  saveProduct(data) {
    return request.post('/api/package/productOperation', data)
  },
  savePriceRule(data) {
    return request.post('/api/package/createTicketPriceRule', data)
  },
  buyCombo(data) {
    return request.post('/api/package/buyCombo', data)
  }
}
```

## 6. 建议后端补充/调整项

为了前端套餐页面更好开发，建议后端补充以下能力：

1. `/productList` 增加 `packageId` 查询条件。
2. `/comboList` 增加套餐子项 include，或新增套餐详情接口。
3. 新增日历价查询接口，例如 `GET /api/package/datePriceList?packageItemId=xx`。
4. 新增套餐详情接口，例如 `GET /api/package/comboDetail?id=xx`，返回套餐主表、子项、价格规则、日历价。
5. 修复 `/createTicketPriceRule` 的房型查询逻辑：应先查 `RoomPackage`，再根据 `roomTypeId` 查 `RoomType`。
6. 修复 `/createTicketPriceRule` 的 `update` 分支，必须加 `where` 条件。
7. 确认下单日期范围是否应该包含离店日。如果是酒店入住，通常离店日不扣房晚库存。
8. 补齐 `itemType=2` 门票套餐购买逻辑。
