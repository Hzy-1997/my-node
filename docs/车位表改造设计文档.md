# 车位表改造设计文档

> 背景：原停车预约只有一个停车场级的 `Parking.availableCount` 永久计数器（下单扣 1、取消/退款回补 1），用户无法选择具体车位，也无法表达"不同时间段同一个车位可重复预约"。
>
> 改造目标：新增**车位表（parking_spots）**，用户预约时选具体车位编号；可用性判断从"永久计数器"改为**时段重叠判断**；`Parking.availableCount` 保留但仅作展示，不再扣减/回补。

---

## 一、表结构设计

### 1.1 新表 parking_spots（模型：`models/appointment/parkingSpotModel.js`）

| 字段       | 类型                 | 说明                                                                           |
| ---------- | -------------------- | ------------------------------------------------------------------------------ |
| id         | INT PK 自增          | 主键                                                                           |
| parkingId  | INT NOT NULL         | 所属停车场ID（FK → parking.id，CASCADE）                                       |
| spotNumber | VARCHAR(20) NOT NULL | 车位编号（如 B1-A03），同停车场内唯一 `uk_parking_spot(parkingId, spotNumber)` |
| area       | VARCHAR(20) NULL     | 区域/楼层（如 B1、地面A区）                                                    |
| spotType   | TINYINT 1/2/3/4      | 1普通 2充电桩 3无障碍 4大型车                                                  |
| status     | TINYINT 1/2          | 1启用 2停用维护                                                                |
| sortOrder  | INT 默认0            | 排序权重                                                                       |

### 1.2 parking_reservation 新增字段（模型：`models/appointment/parkingReservation.js`）

| 字段       | 类型                            | 说明                                                      |
| ---------- | ------------------------------- | --------------------------------------------------------- |
| spotId     | INT NOT NULL DEFAULT 0          | 车位ID（FK → parking_spots.id，无 CASCADE，保留预约历史） |
| spotNumber | VARCHAR(20) NOT NULL DEFAULT '' | 车位编号（**冗余存储**，车位后续改名不影响历史订单展示）  |

另加索引 `idx_spotId(spotId)` 加速时段重叠查询。

### 1.3 可用性判断（核心规则）

某车位在 `[start, end)` 时段可用 ⟺ 不存在该车位的预约单满足：

```js
{
    spotId,                      // 该车位
    status: { [Op.ne]: 2 },      // 未取消（0待确认/1已确认/3已完成 都占时段）
    startTime: { [Op.lt]: end }, // 半开区间重叠判断
    endTime:   { [Op.gt]: start },
}
```

- status=2（已取消，含超时未支付自动取消、退款取消）不占时段
- 未支付（payStatus=1）的预约单**占时段**（下单锁位），10 分钟未支付由定时任务自动取消释放

## 二、接口设计

### 2.1 GET /api/parkingSpots —— 车位列表 + 时段可用性

| 参数                | 必填 | 说明                        |
| ------------------- | ---- | --------------------------- |
| parkingId           | 是   | 停车场ID                    |
| startTime / endTime | 否   | 传了则做时段重叠判断        |
| status              | 否   | 车位状态筛选（1启用 2停用） |

返回：`spotList`（每项含 `available: true/false`）、`availableCount`（可用数统计）。

### 2.2 POST /api/parkingSpotOperation —— 车位管理（管理端）

| action      | 参数                                                | 说明                                                        |
| ----------- | --------------------------------------------------- | ----------------------------------------------------------- |
| create      | parkingId, spotNumber, area?, spotType?, sortOrder? | 单个创建，同停车场编号唯一                                  |
| batchCreate | parkingId, prefix, start=1, count(1-500)            | 批量创建，如 prefix=B1-A, start=1, count=50 → B1-A01~B1-A50 |
| update      | id, spotNumber?, status?, ...                       | 修改（编号改动校验同场唯一）                                |
| delete      | id                                                  | **校验无关联预约记录（含历史）才允许删除**，否则建议停用    |
| list        | parkingId?, status?, page, pageSize                 | 分页列表                                                    |

### 2.3 POST /api/parkingAppointment —— 预约（改造）

入参在原有基础上**新增必填 `spotId`**。流程：

1. 快速预检：用户/停车场/车位存在、车位属于该停车场且启用、时间合法（含**单次预约时长上限 1 小时**）
2. Redis 锁 `parking:lock:${parkingId}` → 事务内：
   - 二次校验车位状态
   - **时段重叠检查**（事务内 double-check，防并发双占）
   - 写入预约单（`spotId` + `spotNumber` 冗余、`writeOffCode` 为独立 6 位核销码）
3. ~~扣减 Parking.availableCount~~（**已删除**，不再扣减）
4. Redis 标记 `parking:pay:expire:${orderNo}`（10 分钟）

返回体新增 `spotNumber`。

## 三、支付/退款/超时链路（配套改动）

### 3.1 支付回调（workers/orderWorker.js，本次补齐）

`processPaymentCallback` 原来只查 Order → PackageOrderDetail → HotelOrder，**没有停车分支，停车订单支付成功后 payStatus 永远不会更新**。已补：

- TRADE_SUCCESS/FINISHED：`payStatus 1→2（已支付）、status 0→1（已确认）、tradeNo、paymentTime`，条件更新（`where payStatus=1`）保证幂等，并清理超时标记
- TRADE_CLOSED：未支付的预约单置 `status=2` 取消，释放时段

### 3.2 退款（publicInterface.js refundHandlers.parking，修复既有 bug）

| 修复项                   | 原错误                           | 修正                        |
| ------------------------ | -------------------------------- | --------------------------- |
| statusField              | `orderStatus`（模型无此字段）    | `payStatus`                 |
| refundableStatuses       | `[2, 4]`                         | `[2]`（payStatus=2 已支付） |
| amountField / calcRefund | `totalPrice`（模型无此字段）     | `orderAmount`               |
| updateRefunded           | `ParkingOrder`（未定义，必报错） | `ParkingReservation`        |
| 退款记录商品名           | `order.parkingName`（不存在）    | `order.title`               |

- 退款更新：`payStatus: 3（已退款）`；未开始/进行中的预约 `status → 2` 释放时段（用 SQL `CASE WHEN status IN (0,1) THEN 2 ELSE status END`，已完成的保留完成状态）
- `restoreParkingStock`：**删除 `Parking.increment` 回补**（计数器已废弃），仅保留清理 Redis 超时标记
- 退款主流程兼容 parking 字段：`tradeNo: order.tradeNo || order.alipayTradeNo`、`userPhone: order.userPhone || order.phone`

### 3.3 超时未支付自动取消（tasks/parkingExpireTask.js，本次新增）

**为什么 Redis 标记不够、必须扫 DB**：`parking:pay:expire:${orderNo}` 只是带 TTL 的哑 key，过期时 Redis 静默删除、不触发任何逻辑，项目也没有 keyspace notification 消费者；且 Redis 重启会丢 key 而 DB 订单仍在待支付。故必须定时扫 DB 对账。

app.js `initializeCronJobs()` 注册，node-cron 每 30 秒扫描：

```
payStatus=1 且 status=0 且 createdAt < 10分钟前 → status=2（超时未支付自动取消）
```

条件更新保证幂等，无需加锁。**这是时段释放的兜底**——未支付预约单占着时段，若不取消会永久锁死该车位时段。

### 3.4 其他业务的超时未支付扫表（tasks/orderExpireTask.js，本次一并补上）

排查发现其他业务同样**没有任何超时未支付扫表**（未支付时支付宝不会推 TRADE_CLOSED 回调，订单永远停在待支付、库存被锁死）：

| 业务                    | 待支付状态    | 取消动作                                                                    | 库存恢复                                                                                                                                                                                              |
| ----------------------- | ------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 票务 Order              | orderStatus=1 | 调 `seckillPayment.handleOrderCancel`（**该函数原本定义了但无任何调用方**） | 内含 Redis `ticket:stock` 回补 + 座位释放补偿                                                                                                                                                         |
| 套餐 PackageOrderDetail | orderStatus=1 | 置 orderStatus=3/verifyStatus=3                                             | Redis `combo:stock` + `hotel:roomtype:stock`；**cancel:data 只有读取没有写入过**，从 DB 推导（roomPackageId→roomTypeId/packageItemId，useDate~useEndDate→dateRange）；DB 只在支付成功才 sync 无需回补 |
| 酒店 HotelOrder         | status=1      | 置 status=5                                                                 | `hotelPurchaseService.refundHotel` 恢复 Redis 房型库存                                                                                                                                                |
| 夏令 campOrders         | payStatus=1   | 置 orderStatus=4                                                            | `TicketType` 计数器回补（sellableCount+1 / soldCount-1）                                                                                                                                              |

超时时长统一 10 分钟；所有更新带"仍为待支付"条件保证幂等；app.js `initializeCronJobs()` 注册，每 30 秒扫描。

## 五、数据库同步（需手动执行）

`bin/www` 启动时 `sequelize.sync({ force: false })` **只会建新表，不会给已有表加列**：

- `parking_spots` 新表：重启后端自动创建 ✅
- `parking_reservation` 加列：**需手动执行以下 SQL** ⚠️

```sql
ALTER TABLE parking_reservation
    ADD COLUMN spotId INT NOT NULL DEFAULT 0 COMMENT '车位ID（关联 parking_spots 表）' AFTER parkingId,
    ADD COLUMN spotNumber VARCHAR(20) NOT NULL DEFAULT '' COMMENT '车位编号（冗余存储）' AFTER spotId;

CREATE INDEX idx_spotId ON parking_reservation (spotId);
```

存量数据 spotId=0、spotNumber=''（历史订单无车位信息，不影响新逻辑：时段重叠查询按 spotId 匹配，历史单不会占用新车位时段）。

车位初始数据可用管理接口批量生成：

```json
POST /api/parkingSpotOperation
{ "action": "batchCreate", "parkingId": 1, "prefix": "B1-A", "start": 1, "count": 50, "area": "B1" }
```
