## 二、完整业务链路（含支付）

停车场预约不是"下单即成功"，而是标准的电商下单→支付→核销链路：

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────┐
│ 1.创建预约   │ ──▶ │ 2.发起支付宝  │ ──▶ │ 3.支付宝异步  │ ──▶ │ 4.核销   │
│  (待支付)    │     │   支付(返回URL)│     │   回调通知    │     │ (已完成) │
│ 扣车位+写单  │     │  前端跳转支付 │     │ 改为已支付    │     │ 凭核销码 │
└─────────────┘     └──────────────┘     └──────────────┘     └──────────┘
       │                                                              ▲
       │              超时未支付(10min)                                │
       └─────────────────▶ 5.自动取消 + 回补车位 ────────────────────────┘ (异常分支)

退款：已支付订单可退款 → 调支付宝退款 → 改为已退款 + 回补车位
```

### 各环节 status / payStatus 流转

| 业务动作         | status   | payStatus | 说明                   |
| ---------------- | -------- | --------- | ---------------------- |
| 创建预约         | 0 待确认 | 1 未支付  | 扣车位、写预约单       |
| 支付成功         | 1 已确认 | 2 已支付  | 回调里更新             |
| 超时未支付       | 2 已取消 | 1 未支付  | 自动取消，回补车位     |
| 用户取消(未支付) | 2 已取消 | 1 未支付  | 回补车位               |
| 核销             | 3 已完成 | 2 已支付  | 凭 writeOffCode        |
| 退款             | 2 已取消 | 3 已退款  | 调支付宝退款，回补车位 |

## 五、续写流程总览（生成订单号之后）

```
1. 参数二次校验（时间合法性）
2. 生成核销码（writeOffCode）
3. 开启数据库事务（确保扣减车位 + 写入预约记录操作成功失败保证数据一致性）
4. 加 Redis 分布式锁（防止车位超卖）
5. 锁内 double check 车位可用数
6. 原子扣减 Parking.availableCount
7. 写入 ParkingReservation 预约记录（status=0, payStatus=1 待支付）
8. 提交事务 / 释放锁
9. 返回 orderNo + writeOffCode + price（前端拿 orderNo 去调支付接口）
```

> 注意：创建预约**不等于预约成功**，此时是「待支付」状态。前端拿到 orderNo 后调用共享 `POST /api/public/payment` 接口发起支付。支付成功后，支付宝回调共享 `/api/public/notify` → 入 Bull 队列 → `orderWorker.processPaymentCallback` 停车场分支会修改 `ParkingReservation` 的 `status` 和 `payStatus` 状态。

### 6.2 生成核销码

```js
// 6位核销码（大写字母+数字）
function generateWriteOffCode(length = 6) {
  const chars = "ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789";
  let code = "";
  for (let i = 0; i < length; i++) {
    code += chars.charAt(Math.floor(Math.random() * chars.length));
  }
  return code;
}
const writeOffCode = generateWriteOffCode();
```

### 6.3 事务 + 分布式锁 + 扣减库存 + 写预约

参考项目 `redisService.acquireLockWithRetry` 与 `seckillPayment.js` 事务写法：

```js
const sequelize = require("../../../mysql/index").sequelize;
const redisService = require("../../../services/redisService");

const lockName = `parking:lock:${parkingId}`;
const lockValue = await redisService.acquireLockWithRetry(lockName);
if (!lockValue) return res.json(util.fail("当前预约人数过多，请稍后再试"));

const t = await sequelize.transaction();
try {
  // 1) 锁内 double check
  const parking = await Parking.findByPk(parkingId, { transaction: t });
  if (!parking) {
    await t.rollback();
    return res.json(util.fail("停车场不存在"));
  }
  if (parking.availableCount <= 0) {
    await t.rollback();
    return res.json(util.fail("可预约车位为0"));
  }

  // 2) 原子扣减车位（带条件，避免负数）
  const [updated] = await Parking.update(
    { availableCount: parking.availableCount - 1 },
    {
      where: { id: parkingId, availableCount: { [Op.gt]: 0 } },
      transaction: t,
    },
  );
  if (updated === 0) {
    await t.rollback();
    return res.json(util.fail("车位已被抢完"));
  }

  // 3) 写入预约记录（待支付状态）
  const reservation = await ParkingReservation.create(
    {
      orderNo,
      parkingId,
      userId,
      phone,
      idCard,
      carNumber,
      startTime: start,
      endTime: end,
      price: parking.price, // 从数据库取，防篡改
      writeOffCode,
      status: 0, // 待确认
      payStatus: 1, // 未支付
    },
    { transaction: t },
  );

  await t.commit();

  // 4) 设置支付超时 key（10分钟），供超时取消判断
  await redisService.setFun(`parking:pay:expire:${orderNo}`, 1, 10 * 60);

  return res.json(
    util.success("预约单已创建，请尽快支付", {
      orderNo,
      writeOffCode,
      reservationId: reservation.id,
      price: parking.price,
      startTime: util.formatTime(start),
      endTime: util.formatTime(end),
      payStatus: 1,
      expireSeconds: 600, // 10分钟内需完成支付
    }),
  );
} catch (error) {
  if (t && !t.finished) await t.rollback();
  return res.json(util.fail(error.message));
} finally {
  await redisService.releaseLock(lockName, lockValue);
}
```

## 八、支付环节（核心补充）

> **架构说明（重要）**：本项目支付/回调/退款三件套**所有业务共用同一组接口**，位于 `routes/managementSystem/publicInterface/`：
>
> | 共享接口                  | 路径                       | 说明                                   |
> | ------------------------- | -------------------------- | -------------------------------------- |
> | `publicInterface.payment` | `POST /api/public/payment` | 发起支付宝支付，返回支付 URL           |
> | `publicInterface.notify`  | `POST /api/public/notify`  | 支付宝异步回调，验签后入 Bull 队列     |
> | `publicInterface.refund`  | `POST /api/public/refund`  | 退款，通过 `refundHandlers` 注册表分发 |
>
> 因此停车场**不需要**单独写 `parkingPay / parkingNotify / parkingRefund` 三个接口，只需要：
>
> 1. **发起支付**：前端直接调共享 `/api/public/payment`，传 `outTradeNo / subject / totalAmount`
> 2. **支付回调**：扩展 `workers/orderWorker.js` 的 `processPaymentCallback`，加一段停车场订单的分支
> 3. **退款**：在 `publicInterface.js` 的 `refundHandlers` 注册表里加一项 `parking` 配置
>
> 这样设计的好处：支付链路代码零重复，新增业务只填配置 + worker 分支即可。

### 8.1 发起支付宝支付（直接复用共享接口）

**不需要新写接口**。前端拿到创建预约返回的 `orderNo` 后，直接调用已有的 `POST /api/public/payment`：

```js

  outTradeNo: orderNo, // 预约单号

  totalAmount: price, // 金额（创建预约时返回的 price）
});
window.location.href = res.data; // 跳转支付宝
```

后端共享接口源码（`routes/managementSystem/publicInterface/publicInterface.js`）已经处理好：
调 `paymentService.createPagePay` 生成支付 URL，`notifyUrl` 写死为 `http://t22c64ca.natappfree.cc/api/public/notify`，`returnUrl` 为前端 `http://localhost:8081/order`。

> ⚠️ **超时校验**：共享 `payment` 接口里没有业务校验（比如停车场 10 分钟超时）。建议在创建预约返回前就告知前端 `expireSeconds`，前端在倒计时结束前才允许发起支付；超时后由定时任务自动取消（见 8.3）。如果非要在发起支付时拦截，可在 `publicInterface.payment` 里加一段按 `outTradeNo` 前缀（`ORDPK`）走业务校验的分支，但不推荐——共享接口应保持业务无关。

**(2) `processPaymentCallback` 里加停车场分支**。在现有 `HotelOrder` 查询之后追加：

```js
async function processPaymentCallback(paymentData) {
  const { out_trade_no, trade_status, total_amount, notifyData } = paymentData;
  try {
    let order = await Order.findOne({ where: { orderNumber: out_trade_no } });
    let isPackageOrder = false;
    let isHotelOrder = false;
    let isParkingOrder = false;

    if (!order) {
      order = await PackageOrderDetail.findOne({
        where: { orderNumber: out_trade_no },
      });
      isPackageOrder = !!order;
    }
    if (!order) {
      order = await HotelOrder.findOne({
        where: { orderNumber: out_trade_no },
      });
      isHotelOrder = !!order;
    }
    // ===== 新增停车场分支 =====
    if (!order) {
      order = await ParkingReservation.findOne({
        where: { orderNo: out_trade_no },
      });
      isParkingOrder = !!order;
    }

    if (!order) throw new Error(`订单不存在: ${out_trade_no}`);

    if (trade_status === "TRADE_SUCCESS" || trade_status === "TRADE_FINISHED") {
      // 停车场用 payStatus===1 判断未支付（其他业务用 orderStatus===1）
      const currentStatus = isParkingOrder
        ? order.payStatus
        : isHotelOrder
          ? order.status
          : order.orderStatus;

      if (currentStatus === 1) {
        if (isParkingOrder) {
          // 金额校验（防篡改）
          if (parseFloat(total_amount) !== parseFloat(order.price)) {
            throw new Error(
              `[PaymentWorker] 停车场订单金额不一致: ${out_trade_no}`,
            );
          }
          await ParkingReservation.update(
            {
              payStatus: 2, // 已支付
              status: 1, // 已确认
              alipayTradeNo: notifyData.trade_no,
              paymentTime: notifyData.gmt_payment,
            },
            { where: { orderNo: out_trade_no, payStatus: 1 } },
          ); // 条件更新，幂等
          // 清除超时标记
          await redisService
            .delFun(`parking:pay:expire:${out_trade_no}`)
            .catch(() => {});
          console.log(
            `[PaymentWorker] 停车场订单支付成功: ${out_trade_no}, 支付时间: ${notifyData.gmt_payment}`,
          );
        } else if (isHotelOrder) {
          // ... 现有酒店分支保持不变 ...
        } else if (isPackageOrder) {
          // ... 现有套餐分支保持不变 ...
        } else {
          // ... 现有票务分支保持不变 ...
        }
      }
    } else if (trade_status === "TRADE_CLOSED") {
      // 停车场订单关闭（用户未付就超时取消，理论上不会走到这；如需处理可调用 cancelParkingReservation）
      if (isParkingOrder && order.payStatus === 1) {
        await cancelParkingReservation(out_trade_no, "支付宝交易关闭");
      }
      // ... 其他业务分支保持不变 ...
    }

    return { success: true };
  } catch (error) {
    console.error(
      `[PaymentWorker] 支付处理失败: ${out_trade_no}`,
      error.message,
    );
    throw error;
  }
}
```

#### 8.2.2 为什么用队列而不是直接在 notify 里改状态

共享 `notify` 接口设计为"**只验签 + 入队 + 立即回 success**"，不在回调里直连数据库。原因：

- 支付宝要求 5 秒内返回 `success`，否则会重试，DB 操作可能超时
- Bull 队列自带重试（`attempts: 3`，指数退避），支付回调可靠性更高
- 多业务共用 notify 时，业务逻辑挪到 worker 里隔离，互不影响

#### 8.2.3 幂等性保证（停车场分支已内置）

- `where: { orderNo, payStatus: 1 }` 条件更新——已支付的不重复更新
- 队列消费者失败重试时，第二次会读到 `payStatus===2`，`currentStatus === 1` 判断不成立，直接跳过

> ⚠️ **签名验证**：共享 `notify` 已经通过 `paymentService.verifyNotifySign(req.body)` 验签，无需在 worker 里重复验签。worker 收到的数据都是可信的。

### 8.3 超时未支付自动取消（定时任务 + 回补车位）

参考项目 `tasks/compensationTask.js` 与 `seckillPayment.js` 的 `handleOrderCancel`。可用两种方式：

- **方案A（推荐）**：定时任务扫描 `payStatus=1 且 createdAt 超过10分钟` 的预约单
- **方案B**：延迟队列（项目有 `queueService`，可加 `addCancelJob`）

抽出的公共取消函数（取消/超时/退款都会用到）：

```js
/**
 * 取消停车场预约（回补车位）
 * @param {string} orderNo 订单号
 * @param {string} reason 取消原因
 */
async function cancelParkingReservation(orderNo, reason) {
  const lockName = `parking:lock:cancel:${orderNo}`;
  const lockValue = await redisService.acquireLockWithRetry(lockName);
  if (!lockValue) throw new Error("取消操作繁忙");

  const t = await sequelize.transaction();
  try {
    const reservation = await ParkingReservation.findOne({
      where: { orderNo },
      transaction: t,
      lock: t.LOCK.UPDATE,
    });

    // 不存在或已取消，直接返回
    if (!reservation) {
      await t.rollback();
      return { success: false, message: "预约单不存在" };
    }
    if (reservation.status === 2) {
      await t.rollback();
      return { success: false, message: "已取消" };
    }

    // 已支付订单不能走这里（要走退款）
    if (reservation.payStatus === 2) {
      await t.rollback();
      return { success: false, message: "已支付订单请走退款流程" };
    }

    // 1. 更新预约单状态
    await ParkingReservation.update(
      { status: 2, cancelReason: reason },
      { where: { orderNo, status: { [Op.ne]: 2 } }, transaction: t },
    );

    // 2. 回补车位（原子 +1）
    await Parking.increment("availableCount", {
      by: 1,
      where: { id: reservation.parkingId },
      transaction: t,
    });

    await t.commit();
    // 清除超时标记
    await redisService.delFun(`parking:pay:expire:${orderNo}`).catch(() => {});
    return { success: true };
  } catch (error) {
    if (t && !t.finished) await t.rollback();
    throw error;
  } finally {
    await redisService.releaseLock(lockName, lockValue);
  }
}
```

## 十、关键设计点说明

### 10.1 为什么创建预约后不算成功

车位是稀缺资源，必须"付款才算锁定"。创建预约只是占位（待支付），10分钟不付自动释放车位给其他用户。

### 10.2 回调的幂等性（重要）

支付宝会重复调用 `notify` 接口，必须保证多次调用结果一致。本项目分两层保证：

- **共享 notify 层**：只验签 + 入队，本身幂等（同一回调入多次队也无所谓）
- **worker 消费层**（`processPaymentCallback` 停车场分支）：
  - `where: { orderNo, payStatus: 1 }` 条件更新——已支付的不重复更新
  - `currentStatus === 1` 判断——重试时读到 `payStatus===2` 直接跳过
  - Bull 队列 `attempts: 3` 指数退避重试，最终一致

> 旧的"行锁 + 事务"方案在 notify 里直连 DB，现在改到 worker 里走条件更新即可，不再需要显式 `t.LOCK.UPDATE`（条件 UPDATE 本身就是原子幂等）。

### 10.3 金额校验防篡改

在 `processPaymentCallback` 停车场分支里比对 `total_amount`（支付宝回调传来）与 `order.price`（DB 里创建预约时写入），不一致直接抛错。`price` 创建时从 `Parking.price` 取，不信任前端。

### 10.4 回补车位的原子性

取消/退款回补车位用 `Parking.increment('availableCount', ...)`，是 SQL 层原子操作，比"先读后写"安全。

### 10.5 超时取消的两种实现

- **定时任务扫描**：简单，但有最多30秒延迟（适合本项目）
- **延迟队列**：精准，项目 `queueService` 已有 `addCancelJob` 可复用
